# Decisions

Each entry: what was chosen, the alternatives, and why. Facts referenced here are listed with links
in [docs/architecture.md](docs/architecture.md#fact-check). Where several options were possible, the
more conservative and safer one was chosen.

## Technology selection

| Layer | Chosen | Alternatives | Why |
|---|---|---|---|
| IaC | AWS CDK (Python), one stack | TypeScript; several stacks | Same language as the pipeline code, so the IoT policy and rule SQL are generated by the same modules that the local stand-ins enforce (D3). One stack keeps destroy and the residual check simple. |
| Device access | AWS IoT Core, MQTT 5 over mutual TLS (port 8883) | Self-managed MQTT broker | Managed broker with per-certificate policies and the thing policy variable; no broker to operate or scale. |
| Device identity | Fleet provisioning by claim for simulators; pre-created certificates for Greengrass cores and the revocation probe | Pre-created certificates only; JITP/JITR; bulk registration | Simulators cannot have keys installed "at the factory", which is the documented use case for provisioning by claim; private keys never leave the simulator's memory. A pre-provisioning hook limits serial format, fleet size and claim client id. JITP/JITR need a registered CA (an account-level change) and are compared in docs/architecture.md. Greengrass cores in containers use the documented manual-provisioning path. |
| Device policy | One policy with `${iot:Connection.Thing.ThingName}` and `iot:Connection.Thing.IsAttached` | One policy per device; wildcard topic grants | One document for any fleet size; isolation is enforced by IoT Core. The only `*` is the job-id segment of the device's own job topics. |
| Greengrass core policy | One policy per core with the literal thing name | Thing policy variables | The Greengrass guide states that thing policy variables are not supported for core devices. Actions are narrowed below the documented minimal policy (component ARN, thing ARN). |
| Edge runtime | AWS IoT Greengrass V2 nucleus in a container (official aws-greengrass-docker Dockerfile at a pinned commit), on ECS Fargate ARM64 | Only the IoT Device SDK; Greengrass on EC2 | The official Docker path is documented for Linux hosts; its Dockerfile targets x86_64 with aarch64 left to the builder. It is built natively on an ARM CodeBuild host. Fargate is not mentioned in the Greengrass docs: whether it works there is a test result, recorded in VERIFICATION.md. The IoT Jobs drill on lightweight simulators demonstrates the same staged-rollout/abort mechanism independently of Greengrass. |
| Device simulation | Two layers: many lightweight simulators (Python, AWS IoT Device SDK v2) in Fargate tasks for scale; a few Greengrass cores for the deployment drill | Greengrass for every simulated device | One Python process holds many MQTT connections; Greengrass cores are heavy (JVM). |
| Message routing | IoT rules → SQS (ingest, telemetry), IoT rule → Lambda (upload URL), IoT rule → DynamoDB (presence) | Rules → Lambda for everything | The queue absorbs bursts in front of the workflow; the upload-URL reply must be synchronous-ish, so it is a direct Lambda action. Every device rule requires `topic(2) = clientid()`. |
| Image upload | S3 presigned POST issued per request, key/type/exact size pinned in the POST policy | Images in MQTT payloads; IoT credentials provider with `credentials-iot:ThingName` | Images are large for MQTT. The presigned POST lets the cloud fix the key and size; the device never holds AWS credentials. The credentials provider is the documented alternative and is used by Greengrass for artifacts (handover note). |
| Orchestration | Step Functions Standard + Lambda (arm64) | Express workflows; one Lambda | Standard is exactly-once with durable history (one execution per image id, name = image id, so replays are idempotent). Retries and the catch-all fallback are visible per step. |
| Generative step | Amazon Bedrock Converse with Amazon Nova 2 Lite through the `us.` inference profile, one forced tool | Nova Lite/Pro in-region; image-generation models; local mock | Nova 2 Lite takes image input and supports a forced tool (`toolChoice.tool`); it is offered only through geographic/global profiles, so IAM lists the profile and its three regional foundation-model ARNs (no region wildcard). No image-generation model: the "background tidy-up" is a deterministic crop onto a plain canvas in code using the validated subject box, which keeps model output out of pixel generation. |
| Injection defence | Two layers: code checks (input re-encoding, schema + content rules, identity from code) and Bedrock Guardrails (image content filters including prompt attack on input, text filters on the draft copy) | Code checks only; Guardrails only | Guardrails are a model-based filter with documented limits for images; the code checks are deterministic and testable offline. Either layer alone is weaker. |
| Registry and shelf | DynamoDB (items, presence) + S3 manifest with conditional writes | RDS; manifest rebuilt from DynamoDB | No database server. S3 `If-Match`/`If-None-Match` prevents lost updates when finalizers run in parallel. |
| Observability | CloudWatch (AWS/IoT metrics, EMF metrics from the functions, alarms, dashboard), IoT lifecycle events | X-Ray only | Native; lifecycle events are on by default and need no account-level setting. |
| Image builds | CodeBuild ARM (`ARM_CONTAINER`, privileged) from a staged S3 asset | Local Docker; CodeBuild Lambda compute | No local Docker on the maintainer machine; Lambda compute cannot build images. |

## Design decisions

- **D1 Identity only from the authenticated connection.** Rules copy the thing name from the topic
  and require it to equal `clientid()`, which the device policy binds to the certificate's thing. The
  dispatcher claims `(thing, image_id)` with a conditional update, so a device cannot reference
  another device's upload, and a replayed message is dropped.
- **D2 Model output never names keys or devices.** Object keys are computed from thing name and
  image id; the model has no tools with side effects; its text is published only after validation,
  and never logged.
- **D3 Policy and rule definitions are data shared by CDK and local mode.** The local broker enforces
  the same policy document, so the local cross-device tests check the deployed policy.
- **D4 Review instead of publish when unsure.** If the model reports instruction-like text or poor
  quality, the image is shelved with neutral copy and status `needs_review`.
- **D5 Fallback, never 5xx or silent drop.** Input rejections, model errors, guardrail
  interventions and validation failures end in a stored result with a fixed reason code and a device
  notification; workflow failures after the fallback raise an alarm.
- **D6 Rate limits and budgets.** A per-device hourly upload counter (DynamoDB conditional update),
  the SQS event-source maximum concurrency, an alarm on Bedrock invocation volume, and an optional
  AWS Budgets cost budget notifying the alarm topic. Budgets are account-wide (no cost-allocation tag
  activation, which is an account-level setting).
- **D7 No inbound network path.** Fargate tasks run in public subnets with public IPs and a security
  group without inbound rules (outbound 443/8883 only); no NAT gateway. VPC interface endpoints are in
  the hardening list.
- **D8 Alarm topic without SSE.** CloudWatch alarms and Budgets cannot publish to a topic encrypted
  with the AWS managed SNS key; a customer managed key would add a KMS key that lingers for a waiting
  period after destroy. Messages contain alarm names and states only.
- **D9 Load-test scale from Service Quotas.** The script reads the applied (or default) quota values
  at run time and uses a fixed fraction of each, so nothing is hard-coded and a shared sandbox keeps
  headroom. Reported results are measurements of that run, not capacity claims.
- **D10 Reconnect strategy is a parameter.** Full-jitter exponential backoff versus immediate
  reconnect are both measured, because the herd effect is what the storm test is for.
- **D11 Lambda on Python 3.14, local toolchain on 3.13.** The bundle is built for the newest Lambda
  runtime (cdk-nag L1); the code is compatible with both and tests run on 3.13.
- **D12 Synthetic fixtures carry a colour marker.** The mock model cannot read text, so each synthetic
  image has a small corner code that tells the mock which case it sees. Real images have none.
- **D13 Unified repository decisions** (standards pass): MIT-0 with the Amazon copyright line;
  vulnerability reports through the AWS vulnerability reporting page; account id placeholder
  `111122223333`; CODEOWNERS `@shaojiez202608`; parameter templates (`config/*.example.json`, live
  copies git-ignored, `make init`); preflight with account confirmation (last 4 digits), destructive
  change guard (`ALLOW_DESTRUCTIVE=1`) and paid-command guard (`ALLOW_PAID=1`); Actions pinned by
  commit SHA (looked up with `git ls-remote`); the ASH job copied unchanged from a repository where it
  ran on GitHub; Conventional Commits; tag `v0.1.0`; no push.
- **D14 Removal policy is a parameter.** The sandbox profile destroys data with the stack; the
  handover profile retains buckets and tables and uses `Teardown=manual-review` (see handover.md).
- **D15 Security exception to the dependency cooldown.** osv-scanner reported High/Critical advisories
  for Pillow 12.3.0; Pillow parses untrusted images, so 13.0.0 is taken although it is younger than the
  7-day cooldown (`exclude-newer-package` in pyproject.toml and the bundle build). Remove the exception
  once the release is older than the cooldown.
- **D16 Existing VPC as a deploy-time option.** Found in testing: the sandbox account had no VPC or
  internet-gateway capacity left. `USE_DEFAULT_VPC=1` places the tasks in the default VPC's public
  subnets (looked up read-only, passed as context, never written to the parameter file); the VPC is not
  modified, only this stack's security group is created in it. The stack still creates its own VPC by
  default.
